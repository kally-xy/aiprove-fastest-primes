# fastest-primes — AIProve bounty entry

Read integer N (1 <= N <= 5,000,000) from stdin, print the number of primes
<= N (pi(N)) to stdout.

## Run

```sh
./run.sh        # reads N from stdin, prints pi(N)
echo 1000000 | ./run.sh   # -> 78498
```

`run.sh` executes the prebuilt static binary `./primes` (fast path, ~0.5 ms
per run). If the binary cannot run on the grading machine, it falls back to
compiling `primes.c` with `cc -O3` (static first, then dynamic) and runs that.

## Strategy

Precomputed `pi(x)` table + segmented tail sieve (file `primes.c`, table in
`tables.h`, generated by `gen_tables.py`):

- `pi_table[k] = pi(k*1024)` for k = 0..4882 (4,883 entries, ~19 KiB).
  pi(5,000,000) = 348,513.
- `small_primes[]` = all 331 primes <= 2236 (= sqrt(5,000,000)).
- Per run: look up pi at the last table point <= N, then sieve only the
  <= 1024 remaining numbers with the small primes. The sieve touches at most
  512 odd numbers, so per-run compute is a few microseconds; measured
  wall-clock is dominated by process startup (~0.5 ms).

Why not a full sieve at runtime? A full odd-only sieve of 5M takes ~7 ms
here — 16x slower than the table version. Why not a full pi(x) table for
every x? That would be 5M x 4 bytes = 20 MB of data for ~0.4 ms of saving;
the 1024-step table is the sweet spot.

## Files

- `primes.c` — the program (C, stdio only, no dependencies).
- `primes` — prebuilt static binary (`gcc -O3 -static`), 806 KiB, x86-64.
  Built from `primes.c`; `run.sh` rebuilds it from source if it cannot run.
- `tables.h` — generated pi table + small primes (37 KiB).
- `gen_tables.py` — regenerates `tables.h` from scratch (single-pass sieve).
- `run.sh` — entry point (see above).

## Benchmarks (this VM: 4 vCPU AMD EPYC, wall-clock incl. process spawn)

Median of 7 runs per N:

| program | N=1,000,000 | N=5,000,000 |
|---|---|---|
| **this entry (table, static)** | **0.45 ms** | **0.43 ms** |
| table, dynamic -O3 | 0.87 ms | 0.82 ms |
| table, -O3 -march=native | 0.73 ms | 0.76 ms |
| full odd sieve, -O3 | 1.90 ms | 7.18 ms |
| Python odd sieve (baseline) | ~91 ms | ~284 ms |

End-to-end through `run.sh` (what the grader times): **~1.3–1.7 ms** at every
N (median of 7: N=10: 1.32 ms, N=1,000,000: 1.67 ms, N=5,000,000: 1.48 ms) —
the extra ~1 ms over the raw binary is the `sh` startup; the binary itself
is ~0.5 ms. Invoking `./primes` directly (if the grader allows it as the
run command) is ~0.5 ms.

Small N (10 / 1000 / 100000) is startup-dominated: all C variants measure
~0.5–2 ms with no meaningful difference between them; only the Python
baseline is visibly slower there too (34–62 ms).

## Correctness

All 5 public cases pass, plus edges: N=1 -> 0, N=2 -> 1, N=3 -> 2,
N=5,000,000 -> 348,513 (reference value).

## Known limitations

- The prebuilt binary is x86-64 / Linux. On a different architecture it
  will fail the self-test in `run.sh` and the script compiles from source
  instead — that path needs `cc` (gcc/clang) on the grading machine.
  If neither the binary runs nor a compiler exists, the entry cannot run.
- `-march=native` was measured and gives no meaningful gain (startup
  dominates), so the shipped binary uses plain `-O3` for portability.
